## 一、项目概述

本项目是一个面向东南大学场景的智能选课平台，前端基于 Vue 3 + Element Plus + axios 构建为 SPA，后端为独立的 Java/Spring 服务（通过 `http://localhost:8080` 通信，本仓库不含后端源码），使用 Redis 承担缓存与临时选课态。

系统面向三类角色：
- **学生** (student)：选课、查询、查看课表
- **教师** (teacher)：课程申报
- **教务** (admin)：审核、自动排课、教室管理、数据重置

核心业务是一条以课程状态机为中心的流程：**教师申报 (0 待审核) → 教务审核通过 (1 待排课) → 自动排课 (2 已发布) / 教务驳回 (3 已驳回)**。

## 二、当前架构分析（As-Is）

### 2.1 整体定位：B/S + 前后端分离

从宏观部署看，这是一个**标准的 Browser/Server 架构**：
- 客户端：浏览器内运行的 Vue SPA（本仓库）
- 服务端：独立的 Spring 后端
- 通信：HTTP + JSON

对应教材中"两层 C/S 的演化形式"——客户端退化为**瘦客户端（浏览器）**，部署与升级成本低。

### 2.2 核心架构风格（多风格叠加）

真实工程中极少单用一种风格，本系统可按层面拆解为：

#### (1) 分层架构 (Layered Architecture)——宏观

| 层 | 承担者 | 实现 |
|---|---|---|
| 表示层 | 浏览器 / Vue SPA | `src/App.vue` 的 `<template>` + Element Plus |
| 业务逻辑层 | 后端 Spring 服务 | `/course/*`、`/classroom/*` 等 endpoint |
| 数据持久层 | 关系库 + Redis | 由 `GET /course/reset-redis` 佐证 |

#### (2) REST 风格（通信层）——但"退化为 RPC 式 HTTP"

`/course/list`、`/classroom/schedule?roomId=` 等以**资源为中心**，`{code, data, msg}` 统一响应格式。但选课等动作把参数放在 query string（`POST /course/select?courseId=`），严格来说违背 REST 的 POST-body 约定——应归为"RPC 风格的 HTTP 使用"。

#### (3) MVVM（前端内部）

- **Model**：`ref`/`reactive` 定义的 `allCourses`、`myCourseList`、`myScheduleCells`…
- **View**：`<template>` 中的声明式模板
- **ViewModel**：Vue 3 的响应式系统 + `computed`（如 `filteredAllCourses`、`pendingAuditCount`）

但是 **MVVM 的实现并不规范**——所有 M/V/VM 代码都堆在单个 `App.vue` 内（约 830 行），违反 MVVM"按业务域分组件 + 独立状态管理"的最佳实践。

#### (4) 基于角色的访问控制 (RBAC-lite)

`currentUser.role ∈ {student, teacher, admin}` 驱动菜单渲染与功能可见性；最终鉴权由后端 sa-token 完成，前端仅做可见性控制。

#### (5) 仓库风格 (Repository)——后端侧推断

三类角色客户端都向同一份后端数据仓库读写，课程状态机由后端集中维护，Redis 作为缓存/临时仓，"一键重置"就是重置这个共享仓。

#### (6) 事件驱动（局部，前端）

Vue 响应式依赖追踪 + Element Plus 组件 emit + `@click` 触发异步 action，是"事件驱动 + 观察者模式"在 UI 内的实现。

### 2.3 4+1 视图

- **逻辑视图**：前端单组件 `App.vue`（内部按 `activeMenu` 区分"页"）+ 后端 REST 资源
- **进程视图**：浏览器进程 ⇄ HTTP ⇄ Spring 进程 ⇄ Redis/DB
- **物理视图**：单机 localhost 部署；前端可静态分发
- **开发视图**：前端 Vite 项目 + 后端 Maven/Gradle 项目
- **场景视图**：登录 → 选课 / 教师申报 → 审核 → 自动排课 → 发布

### 2.4 与教材理论的偏离点

1. **MVVM 的"V/VM 分离"未严格执行**：所有状态都是 `App.vue` 的局部 `ref`，未引入 Pinia/Vuex。
2. **缺少显式的服务层**：`axios.get/post` 散落在业务函数里，没有统一封装。
3. **不是微服务**：后端看起来是单体 Spring，属于传统的**单体 B/S + 集中式数据仓库**范式。

> **一句话总结**：这是一个"B/S + 前后端分离"的单体系统：前端走 MVVM（SPA），后端走"分层 + 集中式数据仓库（关系库 + Redis）"，通过类 REST 的 HTTP 接口通信，并以 RBAC 控制角色视图。

## 三、当前软件的质量问题

### 3.1 安全性

| 问题 | 位置 | 影响 |
|---|---|---|
| Token 存 `localStorage`，易被 XSS 窃取 | `App.vue:428, 675` | 第三方脚本可读 token；应考虑 httpOnly cookie |
| `API_BASE` 用 `http://` 硬编码 | `App.vue:379` | token / 数据明文传输 |
| 鉴权仅在前端菜单级做可见性控制 | `App.vue:42-56` | `localStorage.user_info.role` 可被手动改，**必须靠后端兜底** |
| 所有表单无前端校验 | `teacherForm` (`App.vue:244-269`) | 长度 / 类型 / 注入靠后端 |
| `updatePassword` 是空函数 | `App.vue:670` | UI 上修改密码按钮点了不生效 |

### 3.2 可维护性

| 问题 | 位置 | 说明 |
|---|---|---|
| `App.vue` ~830 行单体组件 | 全文件 | 模板 + 逻辑 + 样式全在一起 |
| 9 个"页面"用 `v-if="activeMenu==='...'"` 串联 | `App.vue:80-361` | 无路由无组件拆分 |
| 无状态管理库 | 全局 `ref` | 跨页共享状态退化为全局污染 |
| 无 API 客户端模块 | `App.vue:529-647` | 换 API 路径需全文件搜索 |
| 拼写错误 `scheduing` | `App.vue:462` | 应为 `scheduling` |
| `HelloWorld.vue` 僵尸文件 | 组件目录 | Vite 脚手架残留 |
| 无 lint / 无 TypeScript | — | 靠人肉 review |

### 3.3 可靠性/健壮性

| 问题 | 位置 | 说明 |
|---|---|---|
| 关键操作缺 `try/catch` | `submitProposal` `:612`；`handleAudit` `:613`；`handleAutoSchedule` `:647` | 后端 500 时 UI 可能错误弹"成功" |
| 空的 `catch` 吞异常 | `handleViewClassroomSchedule` `:576`；`fetchAvailableCourses` `:540` | 用户看不到任何反馈 |
| `handleAutoSchedule` 不判断返回码 | `:647` | 无论成功失败都弹"排课完成" |
| 选/退课每次触发 3 个 fetch | `:588-590, 604-606` | 网络抖动时 UI 数字分 3 次跳 |
| 刷新页面丢失当前菜单 | `:682` | 硬编码 `activeMenu = 'dashboard'` |
| 浏览器后退按钮不工作 | 无 Vue Router | URL 一直停在 `/` |
| 无 `.env` 环境变量 | 整个仓库 0 处 | 换环境只能改源码 |

### 3.4 性能

| 问题 | 位置 | 量级 |
|---|---|---|
| `选课系统背景.jpg` = **4.46 MB** | `App.vue:695` | 首屏阻塞 |
| `seu_logo.png` = **1.30 MB** | 全站 header | 可压到 <50 KB |
| 6 张 avatar × ~780 KB ≈ 4.7 MB | `App.vue:417` | 打开个人信息全部拉下 |
| 课程列表无分页 | `/course/list` | 课程多时列表卡 |
| 课表 `v-show + rowspan` 双重条件 | `App.vue:227, 348` | 脆弱实现 |
| 切页不 abort 上次 fetch | `App.vue:504-510` | 旧请求可能覆盖新数据 |

### 3.5 可测试性

- 无测试框架、无 fixtures、无 mock backend
- 830 行单组件不可单独测试
- 业务逻辑（课表 rowspan、状态机过滤）没被抽成纯函数

### 3.6 可部署性/可移植性

- `API_BASE = 'http://localhost:8080'` 硬编码——无法部署到非本机环境
- 无 `Dockerfile`、无 CI/CD、无构建变量注入
- 后端失败时没有降级页面

### 3.7 可用性

- 所有错误一律 `ElMessage.error('xxx失败')`，信息不足
- 无加载骨架屏
- 表单无校验提示
- 无批量操作、无导出

### 3.8 修复优先级

**🔴 Must-fix（安全 / 正确性）**
1. 后端必须在每个 `/admin/*`、`/course/propose` 上做 role 校验
2. `API_BASE` 改为环境变量 (`import.meta.env.VITE_API_BASE`)
3. `updatePassword` 要么实现，要么禁用按钮

**🟠 Should-fix（可维护性）**
4. 拆组件：`Dashboard / StudentSelect / TeacherPropose / AdminSchedule / ClassroomManage / Profile`
5. 引入 Vue Router + Pinia
6. 抽出 `src/api/*.js` 作为 API 层

**🟡 Nice-to-have（性能 / 体验）**
7. 压缩 public 大图（背景 → WebP，头像 → 96×96）
8. 选课成功后只刷 `fetchMyCourses` + 局部更新，避免 3 连 fetch
9. 补 `.env`、为纯函数写单测

**🟢 Cleanup**
10. 删 `HelloWorld.vue`、改 `scheduing` 拼写、单行函数换行

## 四、架构优化方案（To-Be）

### 4.1 目标五层架构

```
┌──────────────────────────────────────────────────────────┐
│  ① View 层 (pages/ + components/)                        │
│    按业务域拆分：student/ teacher/ admin/ common/         │
├──────────────────────────────────────────────────────────┤
│  ② Router 层 (router/index.js)                           │
│    路径 ↔ 页面；路由守卫做角色鉴权 + 登录拦截             │
├──────────────────────────────────────────────────────────┤
│  ③ State 层 (stores/ · Pinia)                            │
│    useAuthStore / useCourseStore / useScheduleStore       │
├──────────────────────────────────────────────────────────┤
│  ④ Service 层 (api/)                                     │
│    authApi.js / courseApi.js / classroomApi.js            │
├──────────────────────────────────────────────────────────┤
│  ⑤ Infra 层 (utils/http.js, config/)                    │
│    axios 单例 + 拦截器；环境变量；错误上报                 │
└──────────────────────────────────────────────────────────┘
                         ↓ HTTPS / JSON
              后端 (Spring + Redis + DB)
```

这是教材中**分层架构 + MVVM + Repository** 三个风格在前端上的联合应用，每层只依赖下一层，符合**依赖倒置原则**。

### 4.2 按质量属性的优化映射

| 质量属性 | 架构动作 | 对应理论概念 |
|---|---|---|
| 可维护性 | 拆 `App.vue` → 按业务域建 pages + 可复用 components | 关注点分离 / 模块化 |
| 可扩展性 | 新角色/新功能 = 加一个 store + api + 路由 | 开闭原则 (OCP) |
| 可测试性 | 把 `shouldShowCell` / `getCellRowspan` 等抽到 `utils/scheduleGrid.js` | 纯函数 / 无副作用 |
| 可靠性 | axios 拦截器统一重试 + 错误弹窗 | 横切关注点 (AOP) |
| 性能 | 路由级 `lazy import` + 图片 WebP + `AbortController` | 按需加载 / 资源优化 |
| 安全性 | Token 改 httpOnly Cookie；路由 guard + `v-has-role` | 纵深防御 |
| 可部署性 | `.env.development` / `.env.production` + Dockerfile | 12-Factor App |
| 可观测性 | 拦截器中做 log；接入 Sentry；上报 Web Vitals | 横切关注点 |
| 可用性 | 全局 loading store；路由持久化到 URL | 用户心智模型 |

### 4.3 关键重构示意

**`src/config/index.js`**
```js
export const API_BASE = import.meta.env.VITE_API_BASE
export const TOKEN_KEY = 'satoken'
```

**`src/utils/http.js`**（HTTP 基础设施层，AOP 横切）
```js
import axios from 'axios'
import { API_BASE, TOKEN_KEY } from '@/config'
const http = axios.create({ baseURL: API_BASE, timeout: 10000 })
http.interceptors.request.use(cfg => { /* 挂 token + log */ })
http.interceptors.response.use(r => r.data, err => { /* 401 / 5xx 统一处理 */ })
export default http
```

**`src/api/course.js`**（Service 层）
```js
import http from '@/utils/http'
export const listCourses   = () => http.get('/course/list')
export const listAvailable = (major) => http.get('/course/list-available', { params: { major }})
export const selectCourse  = (id) => http.post('/course/select', null, { params: { courseId: id }})
export const proposeCourse = (payload) => http.post('/course/propose', payload)
```

**`src/stores/course.js`**（State 层，Pinia）
```js
export const useCourseStore = defineStore('course', {
  state: () => ({ all: [], available: [], mine: [] }),
  getters: {
    published: s => s.all.filter(c => c.status === 2),
    pendingAudit: s => s.all.filter(c => c.status === 0).length
  },
  actions: {
    async fetchAll() { this.all = await listCourses() },
    async select(id) { await selectCourse(id); await this.fetchMine() }
  }
})
```

**`src/router/index.js`**（Router 层 + 角色守卫）
```js
const routes = [
  { path: '/login', component: () => import('@/pages/Login.vue') },
  { path: '/dashboard', component: () => import('@/pages/Dashboard.vue'), meta: { auth: true } },
  { path: '/student/select', component: () => import('@/pages/student/Select.vue'),
    meta: { auth: true, roles: ['student'] }},
  { path: '/admin/schedule', component: () => import('@/pages/admin/Schedule.vue'),
    meta: { auth: true, roles: ['admin'] }},
]
router.beforeEach((to) => {
  const auth = useAuthStore()
  if (to.meta.auth && !auth.token) return '/login'
  if (to.meta.roles && !to.meta.roles.includes(auth.role)) return '/403'
})
```

**页面组件（View 层）只剩薄薄一层**
```vue
<script setup>
const store = useCourseStore()
onMounted(() => store.fetchAvailable())
</script>
<template>
  <CourseCard v-for="c in store.available" :key="c.id" :course="c" @select="store.select" />
</template>
```

### 4.4 分阶段演进路径

> 不建议大爆炸式重写。按风险从低到高分四步走：

#### 🟢 第 1 阶段：最小侵入（0.5-1 天）
1. `.env.development` / `.env.production` + `VITE_API_BASE`
2. 压缩 `public/` 大图（4.6MB → <200KB，WebP）
3. 删 `HelloWorld.vue`、改 `scheduing` 拼写
4. `updatePassword` 要么实现、要么禁用按钮

#### 🟡 第 2 阶段：架起骨架（2-3 天）
5. 引入 **Vue Router**，把 `activeMenu` 映射成 URL
6. 抽 **`src/utils/http.js`** + **`src/api/*.js`**，集中管理 30+ 处 axios 调用
7. 路由守卫做登录 + 角色校验

#### 🟠 第 3 阶段：状态集中化（3-5 天）
8. 引入 **Pinia**，建 `auth / course / classroom / schedule` 四个 store
9. 拆 `App.vue` → `pages/*`（按角色分三大块）+ `components/{CourseCard,ScheduleGrid,AvatarPicker}.vue`
10. 抽纯函数到 `utils/scheduleGrid.js`

#### 🔵 第 4 阶段：工业化（可选，1 周+）
11. **TypeScript** 迁移（Course、Classroom、ScheduleCell 加 interface）
12. **Vitest** 单测纯函数 + **Playwright** 端到端测试
13. **ESLint + Prettier** 统一风格
14. **Sentry** 前端异常上报 + **Web Vitals** 性能监控
15. **Dockerfile + GitHub Actions CI/CD** + Nginx 部署模板

### 4.5 与教材理论的对应

| 教材术语 | 本次重构的对应 |
|---|---|
| 分层架构 (Layered) | View / Router / State / Service / Infra 五层 |
| MVVM（正确版） | 组件 = V + VM；Pinia store = M（跨组件共享） |
| Repository 模式 | `src/api/` 把后端资源抽象成仓库操作 |
| 横切关注点 / AOP | axios interceptor、router guard、全局 loading |
| 依赖倒置 (DIP) | 页面依赖 store 接口而非 axios 具体实现 |
| 开闭原则 (OCP) | 加新课程类型只新增 store/api，不动老代码 |
| 12-Factor App | 配置外部化、环境变量、无状态前端、一致部署 |

## 五、新架构命名与定位

### 演化前 → 演化后

| 维度 | 演化前 (As-Is) | 演化后 (To-Be) |
|---|---|---|
| 宏观风格 | B/S + 单体后端 | 前后端分离 + 单体后端 |
| 前端内部风格 | 单组件 SPA（反模式 MVVM） | **分层架构 + 正确 MVVM + 单向数据流 (Flux-like)** |
| 组件化 | 1 个组件（`App.vue` 830 行） | **模块化单体 (Modular Monolith)** |
| 通信 | 类 REST (RPC 风格 HTTP) | 类 REST（不变） |
| 状态管理 | 局部 `ref`/`reactive` | **集中式状态仓库 (Pinia, Repository 模式)** |
| 数据访问 | 散落 `axios` 调用 | **API 服务层 (Service Layer Pattern)** |
| 横切关注点 | 仅 token 拦截器 | **AOP 化**：log / auth / error / loading |
| 权限 | 前端菜单可见性 | **路由守卫 + 指令级 + 后端 RBAC** 三层 (纵深防御) |
| 配置 | 硬编码 | **外部化配置 (12-Factor)** |

### 正式命名

> **"前后端分离式 · 分层架构 (5-Layer) · 模块化 MVVM · 基于集中式状态仓库的单向数据流 · SPA"**

每层对应的架构风格：

| 层 | 风格 | 出处 |
|---|---|---|
| ① View | 组件化 (Component-based) | Vue/React 生态 |
| ② Router | 客户端路由 + Front Controller | GoF / EAA |
| ③ State | Flux / Repository + Observer | Facebook Flux, Fowler PoEAA |
| ④ Service | Service Layer | Fowler PoEAA |
| ⑤ Infra | Interceptor / AOP 横切 | Spring AOP 思想 |
| 整体组织 | 分层 + 依赖倒置 + 关注点分离 | Clean Architecture |
| 部署形态 | 模块化单体 (Modular Monolith SPA) | — |

### 为什么不是微前端 / 微服务？

| 风格 | 本次是否采用 | 原因 |
|---|---|---|
| 微前端 | ❌ | 业务规模不够，不需要跨框架独立部署 |
| 微服务后端 | ❌ | 后端业务不复杂（选课 / 排课是强一致单体域） |
| Serverless / BFF | ❌ | 没有多端差异化需求 |
| SSR / SSG | ❌ | 管理后台场景，SEO 不重要 |

保持**"模块化单体"是有意识的取舍**——以最低复杂度获得最大可维护性提升，**架构成熟度与系统复杂度要匹配**。

## 六、进一步演化方向（14 种风格评估）

针对教材中列出的 14 种架构风格，逐一评估对本项目的适配度。

### 6.1 适配度判决表

| 风格 | 适配度 | 落点 | 一句话结论 |
|---|---|---|---|
| 面向方面 (AOP) | 🟢🟢🟢 | 全局横切 | 已部分实现，最该继续强化 |
| 事件驱动 | 🟢🟢🟢 | 前端 UI + 后端状态变更 | 天然贴合，可做实时通知 |
| 基于规则 | 🟢🟢🟢 | 选课 / 排课约束 | 选课本质是规则系统 |
| 正交架构 | 🟢🟢 | 整体组织 | 业务天然正交，分解清晰 |
| 异构风格 | 🟢🟢 | 整体组织 | 本来就是，继续精细化 |
| 管道过滤器 | 🟡 | `auto-schedule` 内部 | 只在排课算法内有用 |
| 解释器 | 🟡 | 选课规则 DSL | 规则复杂到一定程度才值得 |
| 黑板系统 | 🟡 | 智能排课 | 理论贴合，实际过度 |
| C2 风格 | 🟡 | 前端组件通信 | Vue props/events 已是弱化版 |
| 平台/插件 | 🟡 | 课程类型扩展 | 当前 3 种类型，抽象过早 |
| SOA | 🟡 | 后端服务边界 | 粗粒度拆分有价值 |
| 层次消息总线 (HMB) | 🔴 | — | 分布式异构场景，本项目用不到 |
| 微服务 | 🔴 | — | 规模不足，治理成本 >> 收益 |
| 面向 Agent | 🔴 | — | 过度智能化，概念 >> 工程价值 |

### 6.2 强推荐的 5 种风格

#### (1) 面向方面 (AOP)——已起步，继续放大

选课平台天然充满横切关注点——**鉴权、日志、审计、缓存、事务、性能监控**都不是业务核心但必须存在。

| 横切关注点 | 前端做法 | 后端做法 |
|---|---|---|
| 鉴权 | axios interceptor (已有) + `v-has-role` 指令 | `@PreAuthorize("hasRole('ADMIN')")` |
| 日志/审计 | interceptor 打印 + 上报 | `@Around` 切面记录"谁审了哪门课" |
| 缓存 | 请求去重 + stale-while-revalidate | `@Cacheable` 缓存课程列表 |
| 事务 | — | `@Transactional` 保证选课扣库存原子性 |
| 限流 | — | `@RateLimit` 防选课瞬间抢爆 |

#### (2) 事件驱动——"轮询"升级为"推送"

当前 `handleSelect` 后要刷新 3 个接口，天生适合换成事件驱动。

```
  教师申报 ────emit──→ CourseProposedEvent ──┐
  管理员审核 ──emit──→ CourseAuditedEvent ───┼──→ Event Bus (Spring/Kafka)
  自动排课 ────emit──→ ScheduleGeneratedEvent ┘           │
                                                          ↓
                                   ┌────────────┬────────────┬───────────┐
                                   ↓            ↓            ↓           ↓
                              通知服务     日志/审计      Redis 失效    WebSocket
                              (站内信)    (写ES/DB)      (清缓存)     → 前端浏览器
```

**落地**：后端 Spring `ApplicationEvent` / Kafka；前端 WebSocket / SSE 订阅；UI 实时刷新"还剩 23 → 22 个名额"。**收益**：UX 提升 + 去掉 3 连 fetch。

#### (3) 基于规则的系统——选课的本质

选课平台里的业务规则本就繁多，当前全部硬编码：
- 学分上限（本学期 ≤ 30 学分）
- 先修课约束（《算法》必须修过《数据结构》）
- 时间冲突（同一时段不能两门课）
- 容量限制（maxCount）
- 专业过滤（targetMajors）

**演化**：抽到 Drools / Easy Rules 或配置化 JSON：

```json
{
  "name": "本学期学分上限",
  "when": "sum(selectedCourses.credit) + newCourse.credit > 30",
  "then": "reject('超过学分上限')"
}
```

**收益**：教务老师可**直接配置规则**，不用改代码。

#### (4) 正交架构——整体组织原则

选课平台天然有**三个正交维度**：

```
            角色维
           /student/teacher/admin
           │
           ├────────────────────────────→  功能维
           │                              (auth/course/schedule/classroom)
           │
           ↓
          层次维 (view/router/store/service/infra)
```

目录组织上可直接体现：
```
src/
├─ modules/
│  ├─ auth/          ← 功能维"认证"
│  ├─ course/        ← 功能维"课程"
│  │   ├─ student/   ← 角色维
│  │   ├─ teacher/
│  │   └─ admin/
│  ├─ schedule/
│  └─ classroom/
```

**三维各自独立演化**：加新角色只动角色维，加新功能只动功能维，换前端技术栈只动层次维——具备**"正交变化吸收能力"**。

#### (5) 异构风格——整体外壳

本系统本就是异构的，报告里可以正式这样描述：

> 本系统是一个**异构混合架构**：
> - 部署形态：B/S
> - 前端宏观：分层 + 模块化 MVVM
> - 前端组件通信：C2（弱化版，Vue props/events）
> - 前端横切：AOP
> - 后端宏观：分层 + 服务化
> - 后端通信：类 REST（主）+ 事件驱动（辅）
> - 后端业务规则：基于规则引擎
> - 后端排课算法：管道过滤器（局部）

**异构不是混乱**，而是在合适的地方用合适的风格。

### 6.3 可选的 6 种风格

| 风格 | 适用场景 | 要点 |
|---|---|---|
| **管道过滤器** | `/course/auto-schedule` 算法内部 | 课程 → 过滤已排 → 教师偏好 → 教室容量 → 冲突 → 遗传算法优化 → 写入 |
| **解释器** | 复杂选课规则 DSL | 解析 AST → 解释执行 → 判定通过/拒绝 |
| **黑板系统** | 多目标排课优化 | 黑板 = 排课状态；知识源 = 教师/教室/冲突/评分求解器 |
| **C2** | 前端组件总线 | request/notification 消息 + mitt event bus，极致解耦 |
| **平台/插件** | 课程类型可插拔 | `CourseTypePlugin { validator, card, scheduler }` |
| **SOA** | 后端粗粒度拆分 | `Auth / Course / Scheduling / Classroom / Notification` 5 个服务 |

### 6.4 不建议的 3 种风格

| 风格 | 不建议原因 |
|---|---|
| **微服务** | 用户量不到 10K；无多团队协作；强一致性业务（抢课）被分布式事务毁掉 |
| **面向 Agent** | 概念吸引力远大于工程价值，HTTP 请求式选课已够用 |
| **层次消息总线 (HMB)** | 用于分布式异构构件互联，本系统没有异构构件和跨组织集成 |

### 6.5 最终演化愿景

```
┌────────────────────────────────────────────────────────────┐
│              异构架构（顶层组织原则）                       │
├────────────────────────────────────────────────────────────┤
│  前端: 分层 MVVM + AOP 横切 + C2 风格组件通信              │
│  通信: 类 REST (同步) + 事件驱动 WebSocket (异步)          │
│  后端: 分层 SOA (粗粒度服务) + AOP 横切 + 事件驱动         │
│  核心算法:                                                 │
│    ├─ 选课校验: 基于规则 + 解释器                          │
│    └─ 自动排课: 管道过滤器 (+ 黑板作为可选优化)             │
│  整体: 按"功能 × 角色 × 层次"三维正交分解                  │
└────────────────────────────────────────────────────────────┘
```

> 这才是教材意义上"成熟的企业级架构"：**不是一把梭某一种风格，而是多种风格在各自合适的边界内组合**。

## 七、总结

本报告从架构识别、质量评估、架构优化、演化方向四个层面系统分析了本智能选课平台：

1. **当前架构**是典型的"B/S + 前后端分离 + 单体 SPA"，在前端犯了"所有东西堆在 `App.vue` 一个文件"的反模式；
2. **主要质量问题**集中在**安全性（鉴权仅前端）、可维护性（单体组件）、可靠性（空 catch / 硬编码）、性能（4.6MB 背景图）** 四处；
3. **近期重构方向**是把前端按 View / Router / State / Service / Infra 五层重组，用 Vue Router + Pinia + API 服务层 + axios 拦截器，落地**模块化单体 MVVM + 单向数据流**架构；
4. **远期演化方向**以 **AOP + 事件驱动 + 基于规则 + 正交架构 + 异构组织**为主线，辅以管道过滤器（排课算法）和 SOA（后端粗粒度拆分），构成教材意义上"多风格异构组合"的成熟企业级形态。

如果课程报告只能选 3 条主线展开：**AOP（最硬核）、事件驱动 + WebSocket（最有 demo 效果）、基于规则（最有学术深度）**。
