## 一、项目概述

本项目是一个面向东南大学场景的智能选课平台，采用**前后端分离**的 B/S 架构：

- **前端**：Vue 3 + Element Plus + Axios，构建为单页应用（SPA），入口文件 `frontend/App.vue`（约 831 行）
- **后端**：Spring Boot 2.7.14 + Java 8 + MyBatis-Plus + Sa-Token + MySQL + Redis，部署在 `http://localhost:8080`
- **通信**：HTTP + JSON，统一响应格式 `{ code: 200, data, msg }`

系统面向三类角色：

- **学生** (student)：选课、退课、查询、查看课表
- **教师** (teacher)：课程申报
- **教务** (admin)：审核、自动排课、教室管理、数据重置

核心业务是一条以课程状态机为中心的流程：**教师申报 (0 待审核) → 教务审核通过 (1 待排课) → 自动排课 (2 已发布) / 教务驳回 (3 已驳回)**。其中自动排课由后端的 `AutoScheduleService` 实现,采用"体育课优先 → 专业冲突检测 → 教室容量匹配"的三阶段贪心算法。

## 二、当前架构分析（As-Is）

### 2.1 整体定位：B/S + 前后端分离

从宏观部署看，这是一个**标准的 Browser/Server 架构**：

- 客户端：浏览器内运行的 Vue SPA（`frontend/`）
- 服务端：Spring Boot 单体服务（`backend/`）
- 通信：HTTP + JSON，前端通过硬编码的 `API_BASE = 'http://localhost:8080'`（`frontend/App.vue:379`）调用后端

对应教材中"两层 C/S 的演化形式"——客户端退化为**瘦客户端（浏览器）**，部署与升级成本低。后端采用**一体化部署**：Spring Boot 内嵌 Tomcat，单个 JAR 包即可启动。

### 2.2 核心架构风格（多风格叠加）

真实工程中极少单用一种风格，本系统可按层面拆解为：

#### (1) 分层架构 (Layered Architecture)——双层叠加

**宏观三层（前后端整体视角）：**

| 层 | 承担者 | 实现 |
|---|---|---|
| 表示层 | 浏览器 / Vue SPA | `frontend/App.vue` 的 `<template>` + Element Plus |
| 业务逻辑层 | Spring Boot 服务 | Controller → Service → Mapper 三层调用链 |
| 数据持久层 | MySQL + Redis | MyBatis-Plus ORM + Redis 缓存 |

**后端内部四层（微观视角）：**

| 层 | 包路径 | 职责 |
|---|---|---|
| Controller | `controller/` | 接收 HTTP 请求，参数校验，调用 Service，返回 `Result<T>` |
| Service | `service/` + `service/impl/` | 核心业务逻辑（选课、退课、排课、重置），事务管理 |
| Mapper | `mapper/` | MyBatis-Plus 数据访问，映射到 `user_student`、`course`、`classroom` 等表 |
| Entity | `entity/` | 数据实体（`Course`、`Classroom`、`CourseSchedule`、`StudentCourse` 及三类用户表） |

但是分层**并不严格**：`CourseController` 和 `ClassroomController` 中直接注入了 `CourseMapper`、`ClassroomMapper`、`CourseScheduleMapper` 等 Mapper 接口，绕过了 Service 层直接操作数据库。例如 `CourseController.proposeCourse()` 直接调用 `courseMapper.insert(course)`，`ClassroomController.getSchedule()` 在 Controller 中直接写 SQL 查询组装逻辑。

#### (2) REST 风格（通信层）——但"退化为 RPC 式 HTTP"

后端定义了 12 个 HTTP 端点，以资源为中心组织：`/course/list`、`/classroom/schedule?roomId=`、`/user/updateInfo` 等。统一使用 `Result<T>` 包装响应。但存在以下偏离：

- 动作动词放 query string：`POST /course/select?courseId=`、`POST /course/drop?courseId=`，query string 传参而非 request body
- 非标准操作：`GET /course/reset-redis` 是破坏性操作却用了 GET 方法
- `POST /course/auto-schedule` 兼具触发操作和查询双重语义

应归类为"**RPC 风格的 HTTP 使用**"，而非严格 REST。

#### (3) MVVM（前端内部）

- **Model**：`ref`/`reactive` 定义的 `allCourses`、`myCourseList`、`myScheduleCells`…
- **View**：`<template>` 中的声明式模板
- **ViewModel**：Vue 3 的响应式系统 + `computed`（如 `filteredAllCourses`、`pendingAuditCount`）

但是 **MVVM 的实现并不规范**——所有 M/V/VM 代码都堆在单个 `frontend/App.vue` 内（约 831 行），违反 MVVM"按业务域分组件 + 独立状态管理"的最佳实践。

#### (4) 基于角色的访问控制 (RBAC-lite)——前后端协同

前端：`currentUser.role ∈ {student, teacher, admin}` 驱动菜单渲染与功能可见性（仅做可见性控制）。
后端：Sa-Token 框架实现会话管理与鉴权。`SaTokenConfigure` 注册拦截器，排除 `/login`、`/user/register`、`/error`、静态资源及 `OPTIONS` 请求。登录时 `StpUtil.login(userId)` 创建会话，Session 中存储 `role`、`name`、`major`。

角色校验采用**硬编码判断**：在 `CourseController.auditCourse()`、`autoSchedule()`、`resetSystem()` 中手动 `if (!"admin".equals(role))` 而非声明式注解（如 Spring Security 的 `@PreAuthorize`）。

#### (5) 仓库风格 (Repository)

三类角色客户端都向同一份后端数据仓库读写，课程状态机由后端集中维护。Redis 作为选课库存缓存层（key 模式：`course:stock:{id}`、`course:users:{id}`），"一键重置"（`/course/reset-redis`）就清空整个仓库并回滚课程状态。

#### (6) 事件驱动（局部，前端）

Vue 响应式依赖追踪 + Element Plus 组件 emit + `@click` 触发异步 action，是"事件驱动 + 观察者模式"在 UI 内的实现。后端目前**完全没有事件驱动机制**——`AutoScheduleService` 的排课结果是同步返回、同步写库的。

### 2.3 4+1 视图

- **逻辑视图**：
  - 前端：单组件 `frontend/App.vue`（内部按 `activeMenu` 区分 9 个"页面"）
  - 后端：`LoginController` + `CourseController` + `ClassroomController` + `UserController` 四个 REST 控制器，`CourseServiceImpl` + `AutoScheduleService` 两个核心服务
  - 数据实体：`Course`、`Classroom`、`CourseSchedule`、`StudentCourse`、`UserStudent/Teacher/Admin`
- **进程视图**：浏览器进程 ⇄ HTTP（`@CrossOrigin` + OPTIONS 预检放行）⇄ Spring Boot 进程（内嵌 Tomcat）⇄ Redis（库存/用户集合缓存）⇄ MySQL（`course_db` 持久化）
- **物理视图**：单机 localhost 部署；前端 Vite 开发服务器 `:5173`，后端 `:8080`；MySQL `:3306`，Redis `:6379`
- **开发视图**：
  - 前端：Vite 5.4 + Vue 3.5 + Element Plus 2.11 + Axios 1.13，无 TypeScript，无 lint，源代码文件直接位于 `frontend/` 根目录（非标准 `src/` 子目录）
  - 后端：Maven + Spring Boot 2.7.14 + Java 8，Lombok 1.18.30，MyBatis-Plus 3.5.3.1，Sa-Token 1.34.0
- **场景视图**：登录（SHA-256 密码哈希比对 → Sa-Token 签发 session）→ 学生选课（Redis 预减库存 → DB 落库 → 乐观锁并发控制）→ 教师申报 → 管理员审核 → 自动排课（贪心算法，2 学分优先 2 连排）→ 发布

### 2.4 与教材理论的偏离点

1. **MVVM 的"V/VM 分离"未严格执行**：所有状态都是 `frontend/App.vue` 的局部 `ref`，未引入 Pinia/Vuex。
2. **缺少显式的前端服务层**：`axios.get/post` 散落在业务函数里，没有统一封装（后端有 Service 层但前端完全没有）。
3. **后端分层不严格**：Controller 中直接注入 Mapper 操作数据库（`CourseController.proposeCourse()`、`ClassroomController.getSchedule()`），绕过 Service 层。
4. **不是微服务**：前后端都是单体，属于传统的**单体 B/S + 集中式数据仓库**范式。对于当前业务规模，这属于有意识的合理取舍。
5. **认证鉴权未声明式化**：角色校验用 `if` 判断而非 `@PreAuthorize` 注解或 AOP 切面，增加代码重复度和漏检风险。
6. **密码安全不足**：登录时使用 `SaSecureUtil.sha256(rawPassword)` 进行无盐哈希，修改密码（`UserController.updatePassword()`）直接存储明文密码，未做哈希处理。

> **一句话总结**：这是一个"B/S + 前后端分离"的单体系统：前端走 MVVM（SPA），后端走"Controller → Service → Mapper → DB"的四层分层 + 集中式数据仓库（关系库 + Redis），通过类 REST 的 HTTP 接口通信，并以 RBAC（Sa-Token + 前端菜单可见性）控制角色视图。

## 三、当前软件的质量问题

### 3.1 安全性

**前端：**

| 问题 | 位置 | 影响 |
|---|---|---|
| Token 存 `localStorage`，易被 XSS 窃取 | `frontend/App.vue:428, 675` | 第三方脚本可读 token；应考虑 httpOnly cookie |
| `API_BASE` 用 `http://` 硬编码 | `frontend/App.vue:379` | token / 数据明文传输 |
| 鉴权仅在前端菜单级做可见性控制 | `frontend/App.vue:42-56` | `localStorage.user_info.role` 可被手动改，需后端兜底 |
| 所有表单无前端校验 | `teacherForm` (`frontend/App.vue:244-269`) | 长度 / 类型 / 注入靠后端 |

**后端：**

| 问题 | 位置 | 影响 |
|---|---|---|
| 密码无盐哈希（仅 SHA-256） | `LoginController.java:37` | 彩虹表攻击可行；应加随机盐 |
| 修改密码直接存明文 | `UserController.java:74, 80, 86` | 严重安全漏洞 —— `user.setPassword(newPass)` 未哈希 |
| 角色校验为硬编码字符串比较 | `CourseController.java:86, 98, 104` | 易遗漏，不如 `@PreAuthorize` 声明式注解 |
| `@CrossOrigin` 无配置限制 | 全部 Controller | 允许任意源跨域，生产环境应限制白名单 |
| IDOR 漏洞已修复（从 Token 获取 userId） | `CourseController.java:40, 47, 65` | 之前可伪造 `studentId` 参数操作他人选课，现已修复 |
| `/course/reset-redis` 用 GET 方法 | `CourseController.java:102` | 破坏性操作用 GET，CSRF 攻击面大 |

### 3.2 可维护性

**前端：**

| 问题 | 位置 | 说明 |
|---|---|---|
| `frontend/App.vue` ~831 行单体组件 | 全文件 | 模板 + 逻辑 + 样式全在一起 |
| 9 个"页面"用 `v-if="activeMenu==='...'"` 串联 | `frontend/App.vue:80-361` | 无路由无组件拆分 |
| 无状态管理库 | 全局 `ref` | 跨页共享状态退化为全局污染 |
| 无 API 客户端模块 | `frontend/App.vue:529-647` | 换 API 路径需全文件搜索 |
| 拼写错误 `scheduing` | `frontend/App.vue:462` | 应为 `scheduling` |
| `HelloWorld.vue` 僵尸文件 | `frontend/components/` | Vite 脚手架残留 |
| 无 lint / 无 TypeScript | — | 靠人肉 review |

**后端：**

| 问题 | 位置 | 说明 |
|---|---|---|
| Controller 中混杂业务逻辑 | `ClassroomController.getSchedule()` | 50 行 SQL 组装 + 数据转换逻辑直接写在 Controller |
| Mapper 直接注入 Controller | `CourseController.java:20`、`ClassroomController.java:24-25` | 分层被绕过，修改数据访问方式需改 Controller |
| 用户类型用 if-else 分发 | `LoginController.java:45-72`、`UserController.java:35-55`、`UserController.java:71-93` | 相同的三段式 `student/teacher/admin` 判断重复 3 次以上，违反 DRY 原则 |
| 缺少 DTO/VO 层 | 全局 | `Course` 实体同时承担 DB 映射、API 输入、API 输出三种职责 |
| 魔法值散落 | `CourseServiceImpl.java`、`AutoScheduleService.java` | `status == 2`、`"专业课"`、`"体育课"` 等字符串硬编码 |
| `CourseServiceImpl` ~243 行 | 一个类 | 编排了选课、退课、查询、重置等全部课程域逻辑 |

### 3.3 可靠性/健壮性

**前端：**

| 问题 | 位置 | 说明 |
|---|---|---|
| 关键操作缺 `try/catch` | `submitProposal` `:612`；`handleAudit` `:613`；`handleAutoSchedule` `:647` | 后端 500 时 UI 可能错误弹"成功" |
| 空的 `catch` 吞异常 | `handleViewClassroomSchedule` `:576`；`fetchAvailableCourses` `:540` | 用户看不到任何反馈 |
| `handleAutoSchedule` 不判断返回码 | `:647` | 无论成功失败都弹"排课完成" |
| 选/退课每次触发 3 个 fetch | `:588-590, 604-606` | 网络抖动时 UI 数字分 3 次跳 |
| 刷新页面丢失当前菜单 | `:682` | 硬编码 `activeMenu = 'dashboard'` |
| 浏览器后退按钮不工作 | 无 Vue Router | URL 一直停在 `/` |
| 无 `.env` 环境变量 | 整个仓库 0 处 | 换环境只能改源码 |

**后端：**

| 问题 | 位置 | 说明 |
|---|---|---|
| 选课无全局并发锁 | `CourseServiceImpl.selectCourse()` | Redis `decrement` + DB `insert` 不是原子的，高并发下可能超卖 |
| 退课先删记录再还库存 | `CourseServiceImpl.dropCourse()` | 若 `increment` 失败，库存丢失 |
| 乐观锁声明但可能未生效 | `Course.java:32` + `MybatisPlusConfig.java:18` | `@Version` 配置了但 `updateById` 不一定走乐观锁校验 |
| `AutoScheduleService` 无幂等性 | `AutoScheduleService.java:35` | 重复调用会在已排课的课程上追加 Schedule 记录 |
| 全局异常处理只打 `printStackTrace` | `GlobalExceptionHandler.java:29` | 生产环境无结构化日志，排查困难 |

**后端：**

### 3.5 可测试性

**前端：**
- 无测试框架、无 fixtures、无 mock backend
- 831 行单组件不可单独测试
- 业务逻辑（课表 rowspan、状态机过滤）没被抽成纯函数

**后端：**
- 无单元测试、集成测试（`spring-boot-starter-test` 已引入但无任何测试类）
- 业务逻辑与框架强耦合（`CourseServiceImpl` 直接依赖 `RedisTemplate`、Mapper），难以脱离 Spring 容器测试
- `AutoScheduleService` 的排课算法依赖 4 个 Mapper + Redis，无法作为纯算法单独验证

### 3.6 可部署性/可移植性

- `API_BASE = 'http://localhost:8080'` 硬编码——无法部署到非本机环境
- 数据库连接信息硬编码在 `application.yml`（`url: jdbc:mysql://localhost:3306/course_db`）
- 无 `Dockerfile`、无 CI/CD、无构建变量注入
- 后端失败时没有降级页面
- 无 SQL 迁移脚本，数据库 schema 需手动创建和维护

### 3.7 可用性

- 所有错误一律 `ElMessage.error('xxx失败')`，信息不足
- 无加载骨架屏
- 表单无校验提示
- 无批量操作、无导出

### 3.8 修复优先级

**🔴 Must-fix（安全 / 正确性）**

1. **`UserController.updatePassword()` 存储密码前做哈希**（严重安全漏洞）
2. 登录密码加盐（替换 `SaSecureUtil.sha256` 为 salted hash）
3. `@CrossOrigin` 限制生产环境白名单
4. `/course/reset-redis` 改为 POST 方法
5. `API_BASE` 改为环境变量 (`import.meta.env.VITE_API_BASE`)
6. 前端 `updatePassword` 与后端 `/user/updatePassword` 对接（当前前端该函数为空或未调用）

**🟠 Should-fix（可维护性）**

7. Controller 清理：把 `ClassroomController.getSchedule()` 中的业务逻辑抽入 Service；Controller 中移除直接 Mapper 注入

### 正式命名

> **"前后端分离式 · 分层架构 (5-Layer 前端 + 4-Layer 后端) · 模块化 MVVM · 基于集中式状态仓库的单向数据流 · SPA + 模块化单体后端"**

每层对应的架构风格：

| 层（前端） | 风格 | 层（后端） | 风格 |
|---|---|---|---|
| ① View | 组件化 (Component-based) | Controller | Front Controller (GoF) |
| ② Router | 客户端路由 + Front Controller | DTO | DTO Pattern (Fowler PoEAA) |
| ③ State | Flux / Repository + Observer | Service | Service Layer + Transaction Script |
| ④ Service | Service Layer (Fowler PoEAA) | Mapper | Data Mapper (Fowler PoEAA) |
| ⑤ Infra | Interceptor / AOP 横切 | Common | AOP / 全局异常 / 枚举常量 |
| 整体组织 | 分层 + 依赖倒置 + 关注点分离 (Clean Architecture) | 整体组织 | 分层 + 模块化单体 |

### 为什么不是微前端 / 微服务？

| 风格 | 本次是否采用 | 原因 |
|---|---|---|
| 微前端 | ❌ | 业务规模不够，不需要跨框架独立部署 |
| 微服务后端 | ❌ | 选课 / 排课是强一致单体域；抢课场景的分布式事务成本极高 |
| Serverless / BFF | ❌ | 没有多端差异化需求 |
| SSR / SSG | ❌ | 管理后台场景，SEO 不重要 |

保持**"模块化单体"是有意识的取舍**——以最低复杂度获得最大可维护性提升，**架构成熟度与系统复杂度要匹配**。

### 6.2 强推荐的 5 种风格

#### (1) 面向方面 (AOP)——已起步，继续放大

选课平台天然充满横切关注点——**鉴权、日志、审计、缓存、事务、性能监控**都不是业务核心但必须存在。

| 横切关注点 | 前端做法 | 后端做法（现状 → 目标） |
|---|---|---|
| 鉴权 | axios interceptor + `v-has-role` 指令 | 硬编码 `if` → `@PreAuthorize` / `SaCheckPermission` |
| 日志/审计 | interceptor 打印 + 上报 | `System.out.println` → logback + `@Around` 切面记录 |
| 缓存 | 请求去重 + stale-while-revalidate | `@Cacheable` 缓存课程列表 |
| 事务 | — | `@Transactional` 已有，需覆盖退课异常场景 |
| 限流 | — | `@RateLimit` 防选课瞬间抢爆 |

#### (2) 事件驱动——"轮询"升级为"推送"

当前 `handleSelect` 后要刷新 3 个接口，后端排课结果是同步返回的。换成事件驱动后：

```
  教师申报 ────emit──→ CourseProposedEvent ──┐
  管理员审核 ──emit──→ CourseAuditedEvent ───┼──→ Event Bus (Spring ApplicationEvent)
  自动排课 ────emit──→ ScheduleGeneratedEvent ┘           │
                                                          ↓
                                   ┌────────────┬────────────┬───────────┐
                                   ↓            ↓            ↓           ↓
                              通知服务     日志/审计      Redis 失效    WebSocket
                              (站内信)    (写DB)          (清缓存)     → 前端浏览器
```

**落地**：后端 Spring `ApplicationEvent` / Kafka；前端 WebSocket / SSE 订阅；UI 实时刷新"还剩 23 → 22 个名额"。**收益**：UX 提升 + 去掉 3 连 fetch + 后端服务解耦。

#### (3) 基于规则的系统——选课的本质

选课平台里的业务规则本就繁多，当前全部硬编码：

- 学分上限（本学期 ≤ 30 学分）—— 未实现
- 先修课约束（《算法》必须修过《数据结构》）—— 未实现
- 时间冲突（同一时段不能两门课）—— `CourseServiceImpl.selectCourse()` 已实现
- 容量限制（maxCount / Redis 库存预减）—— 已实现
- 专业过滤（targetMajors）—— `CourseServiceImpl.getAvailableCourses()` 已实现
- 排课约束（体育课同专业同时间、专业课互斥等）—— `AutoScheduleService.checkConflict()` 已硬编码

**演化**：抽到规则配置或轻量规则引擎（Drools / Easy Rules）：

```json
{
  "name": "本学期学分上限",
  "when": "sum(selectedCourses.credit) + newCourse.credit > 30",
  "then": "reject('超过学分上限')"
}
```

**收益**：教务老师可**直接配置规则**，不用改代码；排课策略可热更新。

#### (4) 正交架构——整体组织原则

选课平台天然有**三个正交维度**：

```
            角色维
           /student/teacher/admin
           │
           ├────────────────────────────→  功能维
           │                              (auth/course/schedule/classroom)
           │
           ↓
          层次维 (前端: view/router/store/service/infra; 后端: controller/dto/service/mapper)
```

目录组织上可直接体现：

```
frontend/                           backend/
├─ modules/                         ├─ controller/
│  ├─ auth/    ← 功能维"认证"      │  ├─ dto/
│  ├─ course/  ← 功能维"课程"      │  ├─ service/
│  │   ├─ student/ ← 角色维        │  │   ├─ impl/
│  │   ├─ teacher/                 │  │   └─ strategy/  ← 策略模式
│  │   └─ admin/                   │  ├─ mapper/
│  ├─ schedule/                    │  ├─ entity/
│  └─ classroom/                   │  ├─ enums/        ← 枚举常量
                                  │  └─ common/
```

**三维各自独立演化**：加新角色只动角色维，加新功能只动功能维，换前端技术栈只动层次维——具备**"正交变化吸收能力"**。

#### (5) 异构风格——整体外壳

本系统本就是异构的，报告里可以正式这样描述：

> 本系统是一个**异构混合架构**：
> - 部署形态：B/S
> - 前端宏观：分层 + 模块化 MVVM
> - 前端组件通信：C2（弱化版，Vue props/events）
> - 前端横切：AOP
> - 后端宏观：分层 + 模块化单体
> - 后端通信：类 REST（主）+ 事件驱动（辅，远期）
> - 后端业务规则：基于规则引擎（远期）
> - 后端排课算法：管道过滤器（局部）
> - 后端鉴权：AOP（声明式注解）

**异构不是混乱**，而是在合适的地方用合适的风格。

### 6.3 可选的 6 种风格

| 风格 | 适用场景 | 要点 |
|---|---|---|
| **管道过滤器** | `AutoScheduleService.autoSchedule()` 内部 | 课程列表 → 按类型排序 → 过滤不可用教室 → 偏好时间匹配 → 容量检查 → 冲突检测 → 剩余学分填充 → 写入 Schedule |
| **解释器** | 复杂选课规则 DSL | 解析 AST → 解释执行 → 判定通过/拒绝 |
| **黑板系统** | 多目标排课优化 | 黑板 = 排课状态（天×节×教室×专业矩阵）；知识源 = 教师偏好/教室容量/冲突检测/评分函数 |
| **C2** | 前端组件总线 | request/notification 消息 + mitt event bus，极致解耦 |
| **平台/插件** | 课程类型可插拔 | `CourseTypePlugin { validator, card, scheduler }` —— 新增"实验课"类型无需改老代码 |
| **SOA** | 后端粗粒度拆分 | `Auth / Course / Scheduling / Classroom / Notification` 5 个独立服务 |

### 6.4 不建议的 3 种风格

| 风格 | 不建议原因 |
|---|---|
| **微服务** | 用户量不到 10K；无多团队协作；强一致性业务（抢课扣库存）被分布式事务毁掉 |
| **面向 Agent** | 概念吸引力远大于工程价值，HTTP 请求式选课已够用 |
| **层次消息总线 (HMB)** | 用于分布式异构构件互联，本系统没有异构构件和跨组织集成 |

### 6.5 最终演化愿景

```
┌────────────────────────────────────────────────────────────┐
│              异构架构（顶层组织原则）                       │
├────────────────────────────────────────────────────────────┤
│  前端: 分层(5-Layer) MVVM + AOP 横切 + C2 风格组件通信    │
│  通信: 类 REST (同步) + 事件驱动 WebSocket/SSE (异步)      │
│  后端: 分层(4-Layer) 模块化单体 + AOP 横切 + 事件驱动      │
│  核心算法:                                                 │
│    ├─ 选课校验: 基于规则 + 可选解释器                      │
│    └─ 自动排课: 管道过滤器 (+ 黑板作为可选优化)             │
│  数据: MySQL 持久化 + Redis 缓存/并发控制                   │
│  整体: 按"功能 × 角色 × 层次"三维正交分解                  │
│  鉴权: Sa-Token + 声明式注解 (AOP) + 前端路由守卫          │
└────────────────────────────────────────────────────────────┘
```

> 这才是教材意义上"成熟的企业级架构"：**不是一把梭某一种风格，而是多种风格在各自合适的边界内组合**。

## 七、总结

本报告从架构识别、质量评估、架构优化、演化方向四个层面系统分析了本智能选课平台：

1. **当前架构**是典型的"B/S + 前后端分离 + 单体系统"。前端犯了"所有东西堆在 `App.vue` 一个文件"的反模式（831 行）；后端分层不严格（Controller 跨层调 Mapper），且存在**密码明文存储**等安全漏洞；

2. **主要质量问题**横跨前后端：
   - **安全性**：后端 `updatePassword` 存明文密码、SHA-256 无盐哈希、`@CrossOrigin` 无限制；前端 Token 存 localStorage、API_BASE 用 http
   - **可维护性**：前端 831 行单体组件；后端三段式 if-else 泛滥、Controller 含业务逻辑、魔法字符串散落
   - **可靠性**：前端空 catch 吞异常；后端选课无并发锁、排课无幂等性、乐观锁作用存疑
   - **性能**：前端 4.6MB 背景图；后端排课 O(n³) 复杂度、populateScheduleInfo 全表扫描

3. **近期重构方向**：
   - 前端按 View / Router / State / Service / Infra 五层重组，用 Vue Router + Pinia + API 服务层 + axios 拦截器，落地**模块化单体 MVVM + 单向数据流**架构
   - 后端严守 Controller → Service → Mapper 分层，引入 DTO 解耦、策略模式消除重复、枚举替代魔法值、`@PreAuthorize` 声明式鉴权、密码 BCrypt/Argon2 加盐

4. **远期演化方向**以 **AOP + 事件驱动 + 基于规则 + 正交架构 + 异构组织**为主线，辅以管道过滤器（排课算法）和 SOA（后端粗粒度拆分），构成教材意义上"多风格异构组合"的成熟企业级形态。

如果课程报告只能选 3 条主线展开：**AOP（最硬核，横跨前后端所有横切关注点）、事件驱动 + WebSocket（最有 demo 效果，解决 3 连 fetch + 实时通知）、基于规则（最有学术深度，选课约束 + 排课约束可配置化）**。
