# 基于事件驱动风格的架构决策总结

## 1. 总体定位

本系统的核心架构风格应定义为：

> **基于事件驱动风格的前后端分离式智能选课平台架构。**

从实现形态看，系统采用 Vue 3 前端、Spring Boot 后端、MySQL 数据库和 Redis 缓存/库存服务；但从架构协作方式看，系统并不是普通的“请求接口后手动刷新页面”的 CRUD 系统，而是围绕**业务事件的发布、传播与消费**组织关键业务动作。

因此，本系统可以概括为：

> **以事件驱动为核心，分层单体为承载，Vue SPA 与 Spring Boot 应用事件机制协同运行的智能选课系统架构。**

在该架构中，HTTP 主要承担前后端之间的外部触发连接件作用；真正组织业务变化、状态刷新、日志记录和后续扩展的是事件机制。前端通过 `mitt` 事件总线发布和监听事件，后端通过 Spring `ApplicationEventPublisher`、业务事件类和 `@EventListener` 实现事件发布与消费。

## 2. 架构风格选择决策

### 2.1 选择事件驱动作为主架构风格

选课系统的业务天然是一条事件链：

| 业务动作 | 形成的业务事件 | 后续可能触发的反应 |
|---|---|---|
| 教师申报课程 | 课程已申报 | 刷新课程列表、等待管理员审核、记录申报日志 |
| 管理员审核课程 | 课程已审核 | 更新课程状态、刷新待排课列表、记录审核结果 |
| 管理员执行自动排课 | 排课已生成 | 发布课程、初始化库存、刷新课程与课表视图 |
| 学生选课 | 课程已选择 | 刷新我的课程、刷新可选课程、更新课程余量、记录选课日志 |
| 学生退课 | 课程已退选 | 刷新我的课程、返还课程余量、更新课表、记录退课日志 |
| 管理员重置系统 | 系统已重置 | 清空选课数据、重置课程状态、刷新全局视图 |
| 用户登录/退出 | 登录/退出事件 | 恢复或清理本地状态、初始化页面数据 |

这些动作并不是孤立的数据库增删改查。每个动作完成后，都会引发多个后续反应。如果把所有后续反应都直接写在原始操作函数中，业务处理器会逐渐知道太多细节，例如“谁需要刷新”“谁需要记录日志”“谁未来需要收到通知”。这种方式会让代码耦合度升高，也会让新增副作用变得困难。

事件驱动风格的核心价值在于：

| 决策维度 | 事件驱动的作用 |
|---|---|
| 业务表达 | 用事件表达“某个业务事实已经发生”，比直接调用刷新函数更贴近选课流程本质 |
| 模块解耦 | 事件源只负责发布事实，不关心有哪些消费者响应 |
| 扩展能力 | 新增日志、审计、通知、WebSocket 推送时，可以增加监听器而不是改动主流程 |
| 可维护性 | 操作处理逻辑与后续副作用分离，避免单个 handler 或 service 过度膨胀 |
| 演化空间 | 当前可使用进程内事件，未来可平滑升级为消息队列或可靠事件存储 |

因此，本系统的关键架构决策不是简单的“使用前后端分离”，而是：

> **将选课系统中的关键业务动作抽象为事件，并通过发布-订阅机制组织后续反应。**

### 2.2 事件驱动与其他风格的关系

本系统并非只采用单一架构风格，而是以事件驱动为核心，同时使用其他风格作为支撑：

| 架构风格 | 在本系统中的角色 |
|---|---|
| 事件驱动架构 | 组织业务动作传播、状态刷新、日志审计和后续扩展 |
| B/S 架构 | 提供浏览器访问形态，降低客户端部署成本 |
| 前后端分离 | 分离 UI 交互与后端业务规则 |
| 分层架构 | 后端按 Controller、Service、Mapper、Entity 等职责组织代码 |
| SPA/MVVM | 前端通过 Vue 响应式状态驱动视图 |
| 集中式数据仓库 | MySQL 保存主数据，Redis 保存并发辅助状态 |
| 类 REST/RPC over HTTP | 前后端同步请求与响应 |

由此可见，B/S、Vue、Spring Boot、MySQL、Redis 并不削弱事件驱动风格，反而构成了事件驱动架构落地所需的运行环境。

## 3. 架构风格落地方式

### 3.1 前端事件驱动落地

前端采用 `mitt` 作为浏览器进程内事件总线。系统没有让每个按钮操作直接承担所有后续刷新逻辑，而是在业务操作成功后发布事件，再由监听器响应。

前端事件机制主要由以下部分组成：

| 架构元素 | 实现位置 | 职责 |
|---|---|---|
| 事件总线 | `frontend/src/utils/eventBus.js` | 创建全局 `mitt` 实例，作为前端发布-订阅连接件 |
| 事件类型定义 | `frontend/src/events/eventTypes.js` | 统一定义事件名称，避免事件字符串散落 |
| 事件源 | `frontend/App.vue` 中的登录、退出、选课、退课、申报、审核、排课、重置等 handler | 在 API 调用成功后发布业务事件 |
| 事件消费者 | `frontend/App.vue` 的 `onMounted` 注册逻辑 | 监听事件并刷新课程列表、我的课程、课表、系统状态等 |
| 生命周期清理 | `frontend/App.vue` 的 `onUnmounted` | 注销监听器，避免重复注册和内存泄漏 |

前端事件采用“领域:动作结果”的命名方式：

| 事件常量 | 事件名 | 含义 |
|---|---|---|
| `COURSE_SELECTED` | `course:selected` | 学生已经成功选课 |
| `COURSE_DROPPED` | `course:dropped` | 学生已经成功退课 |
| `COURSE_PROPOSED` | `course:proposed` | 教师已经成功申报课程 |
| `COURSE_AUDITED` | `course:audited` | 管理员已经完成课程审核 |
| `COURSE_SCHEDULED` | `course:scheduled` | 管理员已经完成自动排课 |
| `SYSTEM_RESET` | `system:reset` | 系统选课数据已经重置 |
| `AUTH_LOGIN` | `auth:login` | 用户已经登录 |
| `AUTH_LOGOUT` | `auth:logout` | 用户已经退出 |

这种命名方式表达的是“事实已经发生”，而不是“命令某个模块去做事”。例如 `course:selected` 表示选课事实已经成立，至于刷新我的课程、刷新可选课程、刷新课程余量，由监听器决定。

前端典型事件流如下：

```text
用户点击选课
  -> handleSelect 调用后端 /course/select
  -> 后端返回成功
  -> 前端发布 course:selected
  -> 监听器刷新我的课程列表
  -> 监听器刷新可选课程列表
  -> 监听器刷新全部课程列表
  -> UI 基于最新响应式状态重新渲染
```

通过这种方式，`handleSelect` 不需要知道所有后续刷新细节。未来如果新增“选课成功后弹出通知”“刷新仪表盘统计”“写入前端埋点”等需求，只需要新增事件消费者，不需要大幅修改原有选课逻辑。

### 3.2 后端事件驱动落地

后端采用 Spring 原生应用事件机制实现进程内事件驱动。核心结构包括业务事件类、统一事件发布器、异步事件监听器和异步执行配置。

| 架构元素 | 实现位置 | 职责 |
|---|---|---|
| 业务事件类 | `backend/src/main/java/com/example/course/event/` | 描述已经发生的课程、排课、系统事件 |
| 事件发布器 | `CourseEventPublisher` | 封装 Spring `ApplicationEventPublisher`，提供类型安全的事件发布方法 |
| 事件消费者 | `CourseEventListener` | 使用 `@EventListener` 监听业务事件，当前主要承担日志和审计扩展入口 |
| 异步配置 | `AsyncConfig` | 启用 `@Async`，使事件监听器不阻塞主业务流程 |
| 事件发布位置 | `CourseServiceImpl`、`CourseController` 等 | 在核心业务动作成功后发布事件 |

后端业务事件包括：

| 后端事件类 | 触发场景 | 关键数据 |
|---|---|---|
| `CourseSelectedEvent` | 学生选课成功 | 课程 ID、学生 ID、课程名、剩余容量 |
| `CourseDroppedEvent` | 学生退课成功 | 课程 ID、学生 ID、课程名、剩余容量 |
| `CourseProposedEvent` | 教师申报课程成功 | 课程 ID、课程名、教师名 |
| `CourseAuditedEvent` | 管理员审核课程完成 | 课程 ID、课程名、是否通过 |
| `ScheduleGeneratedEvent` | 自动排课完成 | 已排课程数量 |
| `SystemResetEvent` | 系统重置完成 | 操作管理员 |

后端引入 `CourseEventPublisher` 是一个关键设计点。业务代码不直接操作 Spring 原生发布器，而是调用语义明确的方法发布事件。这样做有三个好处：

| 设计点 | 说明 |
|---|---|
| 类型安全 | 发布课程选择、课程退选、排课生成等事件时，参数由方法签名约束 |
| 语义集中 | 事件创建逻辑集中在一个发布器中，业务层不需要到处 `new Event(...)` |
| 便于演化 | 未来若接入 Kafka、RabbitMQ、WebSocket 或审计表，可优先改造发布器和监听器 |

后端典型事件流如下：

```text
前端 POST /course/select
  -> CourseController 获取当前登录学生
  -> CourseServiceImpl 执行选课事务
  -> Redis 预扣减库存
  -> MySQL 写入选课关系
  -> 发布 CourseSelectedEvent
  -> CourseEventListener 异步消费事件
  -> 后端返回 HTTP 响应
```

这里需要注意：事件并不替代核心事务。选课关系、课程状态、排课结果、库存状态等强一致数据仍然在同步流程中完成；事件主要承担解耦副作用、记录日志、支持扩展的职责。

### 3.3 前后端事件协同

当前系统的事件驱动分为前端事件域和后端事件域。二者之间通过 HTTP 请求-响应连接：

```text
前端事件源
  -> HTTP API
  -> 后端业务事务
  -> 后端领域事件
  -> 后端事件监听器
  -> HTTP 响应
  -> 前端 UI 事件
  -> 前端事件监听器
  -> 视图刷新
```

因此，HTTP 在本系统中不是架构主导风格，而是连接两个事件域的同步通信连接件。系统主线仍然是事件：

> **业务动作完成 -> 发布事件 -> 事件消费者响应。**

## 4. 事件驱动架构元素分析

### 4.1 组件

| 组件类型 | 本系统实例 | 职责 |
|---|---|---|
| 事件源 | 前端 handler、后端 Controller/Service | 完成业务动作后发布事件 |
| 事件对象 | 前端事件常量、后端事件类 | 表达“某个业务事实已经发生” |
| 事件连接件 | `mitt`、Spring ApplicationEvent | 负责事件发布、广播和订阅 |
| 事件消费者 | 前端监听器、后端 `CourseEventListener` | 对事件作出响应 |
| 状态承载组件 | Vue 响应式状态、MySQL、Redis | 保存界面状态、主业务数据和并发辅助状态 |

### 4.2 连接件

| 连接件 | 类型 | 作用范围 | 特点 |
|---|---|---|---|
| `mitt` | 浏览器内存发布-订阅总线 | 前端单页应用内部 | 轻量、同步触发、页面刷新后事件不保留 |
| Spring ApplicationEvent | JVM 内发布-订阅机制 | 后端 Spring Boot 应用内部 | 与 Spring 容器集成，支持 `@EventListener` 和 `@Async` |
| HTTP API | 请求-响应连接件 | 前端与后端之间 | 负责跨进程触发业务动作，不负责事件持久化 |
| Redis | 状态连接件/缓存连接件 | 后端与缓存之间 | 支撑课程库存和已选用户集合 |
| MyBatis-Plus Mapper | 数据访问连接件 | 后端与 MySQL 之间 | 负责主数据持久化 |

### 4.3 约束

| 约束类别 | 约束内容 | 目的 |
|---|---|---|
| 发布时机 | 事件必须在业务动作成功后发布 | 避免失败操作产生虚假成功事件 |
| 事件命名 | 事件名使用领域语义，如 `course:selected` | 保持事件含义稳定、清晰 |
| Payload 最小化 | 事件只携带消费者需要的关键数据 | 降低事件源和消费者的数据耦合 |
| 事件不可替代事务 | 核心数据修改仍在同步事务内完成 | 保证选课、排课、库存等强一致性 |
| 消费者独立 | 事件消费者不要求事件源了解自身存在 | 保持发布-订阅解耦 |
| 异步监听风险隔离 | 后端异步监听失败不应破坏主业务响应 | 保证主流程可用性 |
| 生命周期管理 | 前端监听器需要在组件卸载时注销 | 避免重复监听和内存泄漏 |

## 5. 关键架构决策记录

| ADR 编号 | 决策主题 | 决策内容 | 决策理由 | 影响 |
|---|---|---|---|---|
| ADR-001 | 确定事件驱动为主架构风格 | 将选课、退课、申报、审核、排课、重置等关键业务动作抽象为事件 | 选课业务天然是事件链，一个动作会触发多个后续反应 | 系统更易扩展日志、通知、审计和实时刷新 |
| ADR-002 | 前端采用 `mitt` 事件总线 | 在 Vue SPA 内使用轻量级发布-订阅机制 | 当前系统不需要复杂状态管理库，`mitt` 足以支撑跨视图刷新 | 实现简单，但事件不持久化，刷新页面后事件丢失 |
| ADR-003 | 统一前端事件命名 | 使用 `course:selected`、`system:reset` 等领域事件名 | 事件应表达业务事实，而不是命令具体模块执行操作 | 事件语义更稳定，便于新增消费者 |
| ADR-004 | 后端采用 Spring ApplicationEvent | 使用 Spring 原生事件机制完成进程内事件驱动 | 无需引入额外中间件，适合当前系统规模 | 低成本落地，但暂不支持跨进程可靠投递 |
| ADR-005 | 封装 `CourseEventPublisher` | 不让业务代码直接依赖原生 `ApplicationEventPublisher` | 集中事件创建逻辑，提供类型安全发布入口 | 后续可更容易替换为消息队列或审计事件存储 |
| ADR-006 | 后端监听器异步执行 | 使用 `@Async` 处理事件监听逻辑 | 日志、审计、通知属于非核心路径，不应阻塞主事务 | 主流程响应更快，但异步失败需要额外日志和补偿 |
| ADR-007 | HTTP 作为前后端事件边界 | 前后端仍通过 HTTP API 交互 | 浏览器与后端跨进程通信仍适合请求-响应模型 | 架构易调试，但暂未实现端到端实时事件推送 |
| ADR-008 | 事件不替代同步事务 | 选课、退课、排课、重置等主数据修改仍在同步事务中完成 | 课程库存和选课关系需要强一致性 | 数据可靠性更高，事件主要负责解耦副作用 |
| ADR-009 | Redis 支撑选课事件背后的并发状态 | 用 Redis 维护课程库存和已选用户集合 | 选课动作存在并发压力，Redis 更适合快速扣减和判断 | 性能提升，但需要关注 Redis 与 MySQL 一致性 |
| ADR-010 | 课程生命周期事件化 | 把课程申报、审核、排课、发布、选择、退选、重置视为事件链 | 课程不是静态数据，而是在流程中持续演化的对象 | 有利于流程追踪、日志审计和后续可视化 |
| ADR-011 | 暂不引入外部消息队列 | 当前采用前端内存事件总线和后端进程内事件机制 | 系统规模和部署复杂度暂不需要 Kafka/RabbitMQ | 架构保持简单，但未来可靠投递需求出现时需升级 |
| ADR-012 | 保留分层架构作为承载结构 | 后端继续使用 Controller、Service、Mapper、Entity、Event、Config 等包结构 | 事件驱动负责业务传播，分层负责代码职责划分 | 两种风格互补，而不是互相替代 |

## 6. 架构决策总结

本系统最重要的架构特征不是“用了 Vue 和 Spring Boot”，也不是“前后端分离”，而是把选课平台中的核心业务动作事件化，并通过前后端两个事件域实现解耦。

系统的主运行逻辑可以总结为：

```text
用户操作
  -> 触发业务动作
  -> 后端完成强一致状态修改
  -> 后端发布领域事件
  -> 后端监听器异步处理日志、审计和扩展逻辑
  -> 前端收到成功响应
  -> 前端发布 UI 事件
  -> 前端监听器刷新相关视图状态
```

这种架构使系统具备以下特点：

| 特点 | 说明 |
|---|---|
| 主线清晰 | 以“业务事件发生”为系统运行主线 |
| 解耦明显 | 事件源不直接依赖所有后续消费者 |
| 扩展方便 | 新增日志、通知、审计、统计、推送时可增加监听器 |
| 复杂度适中 | 使用进程内事件机制，避免过早引入消息队列 |
| 与业务匹配 | 选课、审核、排课、退课、重置本身就是连续事件链 |

因此，报告中可以将本软件的架构正式命名为：

> **基于事件驱动风格的前后端分离式智能选课平台架构。**

也可以在更完整的表述中写成：

> **本系统采用事件驱动为核心、分层单体为承载、Vue SPA 与 Spring Boot 应用事件机制协同的混合架构。系统通过前端 `mitt` 事件总线和后端 Spring ApplicationEvent 机制，将选课、退课、课程申报、课程审核、自动排课、系统重置等关键业务动作抽象为事件，并以发布-订阅方式组织状态刷新、日志审计和后续扩展，从而降低业务模块之间的直接耦合。**
